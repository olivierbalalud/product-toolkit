# 5. Worktrees and Parallelism

How several PRDs are designed and several slices built at the same time without colliding. Decision IDs in brackets point to [`../grilling-log.md`](../grilling-log.md). Facts about Claude Code come from its [worktrees](https://code.claude.com/docs/en/worktrees) and [hooks](https://code.claude.com/docs/en/hooks) documentation, checked on 2026-10-20.

**Principle:** we use Claude Code's own worktree mechanism and wrap it with small scripts, rather than override it [R16-P, R16-Q0].

## 5.1 Three levels of parallel work

| Level | Unit | Isolation | Limit | Decision |
|---|---|---|---|---|
| Design | One PRD in *Exploring* | A `design/` worktree, frontend only | 3 per driver | R1-Q10, R4-Q6 |
| Development | One slice | A `slice/` worktree with its own environment | 2 per developer | R1-Q10, R4-Q6 |
| Inside a slice | One ticket | A subagent worktree, created and removed by Claude Code, based on the slice branch | As many as the ticket graph allows | R4-Q7′ |

Files don't collide because each PRD has its own folder [R3-Q1c]. **Shared layers** collide easily, so they change only in their own enabler slice, one at a time: tokens, `globals.css`, design-system components, OpenAPI shared by several apps, and database migrations [R2-Q9].

## 5.2 Names

| Kind | Branch | Worktree | Commit scope | Decision |
|---|---|---|---|---|
| Design of a PRD | `design/PRD-012.1-<slug>` | `design-PRD-012.1-<slug>` | `PRD-012.1` | R4-Q5′ |
| Design change request | `design/DCR-012.1-01-<slug>` | `design-DCR-012.1-01-<slug>` | `DCR-012.1-01` | R10-Q1 |
| Slice | `slice/PRD-012.1-<slug>` | `slice-PRD-012.1-<slug>` | `PRD-012.1` | R4-Q5′ |
| Enabler slice | `enb/ENB-004-<slug>` | `enb-ENB-004-<slug>` | `ENB-004` | R4-Q5′ |
| ADR draft or spike | `adr/ADR-0007-<slug>` | `adr-ADR-0007-<slug>` | `ADR-0007` | R4-Q5′ |
| Work outside the lifecycle | `fix/…`, `chore/…`, `docs/…`, `ci/…` | same, `/` → `-` | as needed | R4-Q5′ |
| Ticket inside a slice | generated by Claude Code | generated, e.g. `bold-oak-a3f2` | the ticket's PRD | R4-Q5′ |

The worktree name is the branch name with `/` replaced by `-`, so the design and slice worktrees of one PRD never collide.

## 5.3 What Claude Code provides, and the gap we fill

What Claude Code does on its own:

- `claude --worktree <name>` creates `.claude/worktrees/<name>/` on a **new** branch `worktree-<name>`. It cannot open an existing branch. But if a folder `.claude/worktrees/<name>/` **already exists**, `--worktree <name>` reopens it.
- `.worktreeinclude` copies gitignored files such as `.env.local` into new worktrees.
- Subagents with `isolation: worktree` get their own worktree, removed when they finish without changes; a periodic sweep removes old ones. Worktrees you create yourself with `git worktree add` are never swept.

Two gaps remain: our **branch names**, and a **running environment** (ports, Compose project, database) per worktree. We fill them with scripts in the monorepo, not by replacing Claude Code's mechanism with a `WorktreeCreate` hook. A hook would replace creation for *every* worktree, subagents included, switch off Claude Code's cleanup and `.worktreeinclude`, and make every worktree depend on our script [R16-Q0].

Add `.claude/worktrees/` to `.gitignore`.

## 5.4 Start scripts

| Command | Does | Then launches |
|---|---|---|
| `make design PRD=PRD-012.1 SLUG=book-room` | Creates or opens `design/PRD-012.1-book-room` in `.claude/worktrees/design-PRD-012.1-book-room`; starts the web app alone, on its own port, against MSW mocks | `claude --worktree design-PRD-012.1-book-room` |
| `make dcr DCR=DCR-012.1-01 SLUG=new-copy` | The same for a design change request | `claude --worktree design-DCR-012.1-01-new-copy` |
| `make slice PRD=PRD-012.1 SLUG=book-room` | Creates or opens `slice/PRD-012.1-book-room`; runs `make env-up` in it | `claude --worktree slice-PRD-012.1-book-room` |
| `make enb ENB=ENB-004 SLUG=ci` | The same for an enabler slice | `claude --worktree enb-ENB-004-ci` |

Each script:

1. creates the branch from `origin/main` if it doesn't exist, or opens it if it does;
2. runs `git worktree add .claude/worktrees/<name> <branch>`, unless the folder already exists;
3. copies the files listed in `.worktreeinclude`, since this worktree is created by `git` and not by Claude Code;
4. sets up the environment for its kind (§5.5);
5. launches Claude Code on that folder.

Run the scripts from the main checkout. Exiting Claude Code leaves the worktree in place; it was created by the script, so Claude Code's sweep never removes it.

## 5.5 Environments

### Shared per machine

**One shared instance per machine** of the stateful and heavy services, started once: PostgreSQL 16 with pgvector, matching production, and any model service. The product's embedded models are memory-hungry, so one copy per worktree would not fit [R16-Q1].

Development and tests stay on PostgreSQL. Doltgres was assessed and rejected for now: it lacks row-level security policies, pgvector indexes and role switching, and doesn't support the team's driver and migration tool. Revisit through an ADR once it does ([research](../research/dolt-for-dev.md)) [R16-Q4].

### Per worktree: `make env-up`

`make env-up`, run inside any worktree [R16-Q0, R16-Q1]:

1. runs `make env-prune` first (§5.6);
2. allocates a block of ports and a `COMPOSE_PROJECT_NAME`, keyed on the worktree's path;
3. creates the worktree's database on the shared PostgreSQL by **cloning a migrated template** (`CREATE DATABASE … TEMPLATE …`), kept at the migration head of `main`, then applies the branch's own new migrations [R16-Q4];
4. starts the worktree's own app processes (web, API) on its ports;
5. writes everything to a gitignored `.env.worktree`.

It is idempotent: running it again in the same worktree reuses what exists.

| Worktree | Environment | Decision |
|---|---|---|
| Design | Web app only, on its own port, against MSW mocks of the draft contract. No database. | R2-Q9 |
| Slice and enabler | `make env-up`, from the start script | R2-Q9, R16-Q0 |
| Subagent (ticket) | Nothing by default. `make test-integration` and `make test-ui` call `make env-up` themselves, so a ticket that needs a database or a running app gets one automatically. Business-layer tests need neither. | R16-Q2′ |

## 5.6 Cleaning up

- **Worktrees:** Claude Code removes subagent worktrees itself. Remove a design or slice worktree once its PR has merged, with `git worktree remove`.
- **Environments:** `make env-prune` drops the database and frees the ports of every environment whose worktree folder no longer exists, and lists, without touching, those whose worktree still exists. `make env-up` runs it first, so leftovers are cleaned up whenever any environment starts; it can also be run by hand [R16-Q3′].
- `git worktree list` shows every worktree.

## 5.7 What all worktrees share

From the Claude Code docs:

- **The repository's `.git`:** commits made in any worktree land in the same repository.
- **Plugins installed at project scope** load in every worktree of the repository, so our plugin doesn't need reinstalling per worktree.
- **Permission approvals** ("don't ask again") are saved to the main checkout's `.claude/settings.local.json` and apply to every worktree.
- **Hooks:** `${CLAUDE_PROJECT_DIR}` keeps pointing at the main checkout; a hook that needs the worktree reads the `cwd` field of its input.

## 5.8 Limits and queueing

- At most **3 PRDs in *Exploring* per driver** and **2 slices in development per developer** [R4-Q6].
- **Enabler slices that block feature slices go first** [R4-Q6].
- With two founders, both sign every design gate, so up to six design reviews can queue. Unblock enablers first, then finish reviews, then start new work.
